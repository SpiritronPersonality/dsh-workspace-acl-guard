# 缺陷报告：DSH 沙箱对工作区根写入常驻安全描述符

**产品**：DeepSeek Harness（Windows 桌面客户端）
**平台**：Windows 11 简体中文（个人工作站）
**影响版本**：0.2.x（本文以 0.2.2-rc.1 代码与现场为准；更早版本存在不同签名，见 §5）
**严重级别**：高——症状与 DSH 完全无关，用户会先怀疑系统；已造成两次系统重装
**状态**：机制已定位，现场已修复；建议产品侧修复

> 本文是公开版：用户 SID、账户名与部分路径已替换为占位符。

---

## 1. 摘要

DSH 在 Windows 上以 `workspace-write` 模式运行第一条受限命令时，会对**会话工作区根目录**做一次**常驻**的安全描述符改写，同时写入三样东西：

1. 一个按工作区路径派生出来的能力 SID（`S-1-4-*`）允许项；
2. 一条 `Everyone` 的「删除子目录和文件」（`FILE_DELETE_CHILD`）拒绝项；
3. 一个 Low 完整性标签（`no-write-up`，可继承）。

这次改写**不随会话结束回滚**（源码注释明确为“常驻、复用缓存、绝不撤销”）。当用户把工作区设成桌面、文档、应用目录这类真实目录时，目录会脱离 Windows 的继承链与默认策略，产生与 DSH 界面毫无关系的故障：桌面快捷方式全部变白、文件夹本地化名称退回英文、双击提示“未知发布者”。在应用目录或代码仓库上，故障表现为更难归因的“保存失败 / 更新失败 / 删不掉 / 构建异常”。

本文给出两个现场样本、代码层证据、最小复现、以及一个只读检测工具（同仓库发布）。

---

## 2. 现象

### 2.1 桌面（可观测性最高）

- 桌面**所有** `.lnk` 图标变成通用白纸图标；文件夹图标正常；双击仍能打开。
- 桌面文件夹显示名从「桌面」退回英文 `Desktop`；同级的「文档」「下载」仍是中文。
- 双击快捷方式弹出“未知发布者”。
- 以上只在**图标缓存被重建之后**出现（装软件、重启 explorer、系统清理都会触发），因此表现为“昨天还好、今天突然全坏”。

### 2.2 任意工作区（更隐蔽）

同一套改写发生在任何被设为工作区的目录上。现场第二个样本是一个项目内子目录（`<PROJECT>\XIANGLING`），它的 DACL 至今仍是保护态、含能力 SID 与 `Everyone` 拒绝：

```
D:PAI(D;CI;DT;;;WD)(A;OICI;0x110156;;;S-1-4-<CAP>)(A;;FA;;;BA)...
S:AI(ML;OICI;NW;;;ME)
```

这里没有图标可坏，所以没有人会发现——但它已经脱离继承链，任何依赖 Windows 默认权限的工具（安装器、更新器、备份/同步、受限令牌进程）都可能出现难以解释的行为。

**结论：这不是“桌面问题”，是“工作区根问题”。桌面只是可观测性最高的样本。**

---

## 3. 现场证据

### 3.1 样本 A：桌面

用 `icacls` / 安全属性页可看到两条**显式（非继承）**规则：

| 主体 | 类型 | 权限 | 继承 |
|---|---|---|---|
| `Everyone` | 拒绝 | 删除子目录和文件 | 非继承（显式） |
| `S-1-4-<CAP>` | 允许 | 删除子目录和文件 / 写入 / 删除 | 非继承（显式） |

对照同机 `Documents`：只有三条**继承**规则（SYSTEM / Administrators / 当前用户），无任何显式项。

判定依据：

1. 只在 DSH 以该目录为工作区跑过之后出现；
2. 两次重装后仍复发——只要 DSH 再次以该目录为工作区启动，规则就重新写回；
3. `S-1-4-*` 属于 NT NON UNIQUE AUTHORITY，不是 Windows 为普通用户/组分配的常规主体。

### 3.2 样本 B：项目内目录

见 §2.2。该样本的标签是 `ME`（Medium）、拒绝项是 `DT`（Delete）——与 0.2.2 的写法（`0x40` + Low 标签）不同，说明**至少存在两代不同的写入签名**。这正是“只认特征码会漏”的原因。

### 3.3 修复有效性

按 §6 清理两条规则并恢复继承、重建图标缓存后：图标恢复彩色、「桌面」显示名恢复、双击不再弹窗。

**已验证：清理 ACE 后症状消失。**
**未验证：为什么这两条规则会导致外壳解析失败（见 §7）。**

## 4. 代码层证据（0.2.2-rc.1）

`@deepseek-ai/dsh-sandbox-windows-acl` 的授权路径：

- 读当前安全描述符：`GetNamedSecurityInfoW(path, SE_FILE_OBJECT, DACL|LABEL)`；
- 合并三条条目后，**一次** `SetNamedSecurityInfoW(path, SE_FILE_OBJECT, DACL|LABEL, ...)` 写入；
- 能力 SID 由规范化工作区路径**确定性派生**（同一路径永远同一个 SID）；
- 拒绝项：`Everyone` + `FILE_DELETE_CHILD(0x40)`，仅容器继承；
- 标签：`SYSTEM_MANDATORY_LABEL_ACE` 指向 Low（`S-1-16-4096`），`no-write-up`，可继承；
- 工作区授权**常驻**：会话结束、实例销毁都不撤销，只有临时授权会被回收。

前置条件（与第二个故障直接相关）：

- 被授权目录必须由调用者拥有，或显式授予 `WRITE_OWNER`（标签在 SACL，合并写入需要它）；
- 若目录所有者是**另一个账户**、当前用户只有继承来的 Modify（典型：旧系统迁移、重装后保留的数据盘），授权会以 Win32 错误 5 失败；
- 失败后命令无法在沙箱中运行。现场表现为：**每条命令都弹一次授权提示**，用户感知为“沙箱坏了”。

现场 `acl-report` 记录（2026-11-05）：目录 owner 为旧账户 SID，当前用户 `writeDac=false`，判定 `PRECONDITION`，修复被拒。之后用管理员一次性补 `FullControl` 才恢复。

---

## 5. 为什么难以归因

1. **症状不在 DSH 里**：白图标、英文名、未知发布者，第一反应是系统、杀软或“自己乱装软件”。
2. **延迟显形**：改写发生在首条命令，故障要等图标缓存重建才出现，时间上与“最近装了什么”错位。
3. **没有日志**：改写静默完成，DSH 侧无任何用户可见记录；Windows 事件日志也没有对应条目。
4. **常规修复“成功但无效”**：`sfc`、`DISM`、重装累积更新、保留文件重装、重建图标缓存——全部返回成功，全部无效，进一步把人引向系统故障。
5. **两次重装**：ACL 与相关状态被保留，重装不解决问题，却损失了 C 盘开发环境与部分桌面文件。

---

## 6. 最小复现

> 请在一台可回滚的测试机或虚拟机里做；不要拿主力机的桌面试。

1. 干净 Windows 11（简体中文），桌面放 3 个指向不同 `exe` 的快捷方式；
2. 记录基线：`icacls "%USERPROFILE%\Desktop"`，确认图标彩色、「桌面」显示名正常；
3. 用 DSH 把工作区设为 `%USERPROFILE%\Desktop`，执行一次写文件/改名；
4. 再取 `icacls`：应出现 §3.1 的两条显式规则；
5. 记录完整性标签（`icacls` 看不到，需要读 SACL）：

```powershell
# 输出形如 ...S:AI(ML;OICI;NW;;;ME)
# ME=Medium（正常），LW=Low（DSH 新版会写）
```

6. 关闭 DSH 会话 → 规则**仍然残留**；
7. 重建图标缓存 / 重启 explorer / 重启系统；
8. 观察：全部 `.lnk` 变白、「桌面」变 `Desktop`、双击弹未知发布者；
9. 清理并恢复继承：

```bat
icacls "%USERPROFILE%\Desktop" /remove:d Everyone
icacls "%USERPROFILE%\Desktop" /remove:g *S-1-4-<CAP>
icacls "%USERPROFILE%\Desktop" /inheritance:e
```

10. 重建缓存 → 观察是否恢复。

仓库内 `docs/REPRODUCE.ps1` 会把第 2、4、5 步自动化：同时抓 DACL 与标签，输出前后对比表。

## 7. 机制判定：已验证 vs 未验证

**已验证**

- 改写是真实的、显式的、可重复的；
- 改写不随会话结束撤销；
- 清理后症状消失（至少一例，桌面）。

**未验证（假设）**

- 外壳的图标与本地化名称解析，为什么会被这两条规则拒绝。抓到的拒绝项只针对“删除子目录和文件”，理论上不拦读取；因此真正的原因可能是：
  - Low 完整性标签（`no-write-up`）在外壳的受限令牌/AppContainer 解析路径上被拒；
  - 保护态 DACL 切断了继承，使外壳进程拿不到它预期的访问；
  - 未知主体 SID 让某些解析器回退。
- 需要在外壳解析路径上抓 HRESULT 才能定性。

**已排除**

- 本地化资源缺失：`desktop.ini`、`FolderDescriptions`、`shell32.dll.mui` 全部正确；
- 图标缓存残留：把彩色快捷方式复制到新位置再取图标，仍是白图标；
- 语言/注册表损坏：`shell:Desktop` 解析结果仍是「桌面」。

## 8. 影响

| 类别 | 后果 |
|---|---|
| 体验 | 桌面全白、显示名英文、每次打开弹“未知发布者” |
| 数据与环境 | 两次重装导致 C 盘开发环境（Python/Node/Git/venv）与部分桌面文件丢失 |
| 信任 | 故障表现与 DSH 无关，用户先怀疑系统而非产品 |
| 隐蔽性 | 同样的改写发生在应用目录/代码仓时，几乎无人能归因 |

---

## 9. 建议

### 产品侧（必须）

1. **禁止对“已知文件夹”根目录做工作区授权**：工作区等于 Desktop / Documents / Downloads / OneDrive / 开始菜单 / 用户主目录 / 盘根时，拒绝并提示，或强制在其下创建 `.dsh\workspace`；
2. **只允许“追加授权”**：不得添加显式 `Deny Everyone`，不得引入非标准主体 SID，不得切断继承链。

### 产品侧（应该）

3. 会话开始保存 DACL/SACL 快照，结束或异常退出时回滚；
4. 启动自检：发现历史污染（`Everyone Deny` / `S-1-4-*` / Low 标签）时给出一键清理；
5. 图标解析兜底：检测到 `.lnk` 图标批量失败时提示可能原因。

### 产品侧（可选）

6. 文档与 UI 明示“不要把工作区设在桌面等系统文件夹”。

### 用户侧兜底

- 工作区迁出桌面与所有应用目录（`C:\dsh-work` 之类）；
- 按 §6 第 9 步清理历史 ACE；
- 重装后验收三项：图标彩色 / 显示名「桌面」 / 双击不弹窗；
- 用本仓库的只读检测工具定期比对基线。

---

## 10. 未确认项

1. **ACL → 图标/名称失效的精确机理**未证实（见 §7）；
2. 同期系统中存在**组件版本错位**（`explorer.exe` / `shell32.dll` / 组件库三套版本不一致），可能是叠加因素，也可能是独立问题；重装后已消失；
3. 两次重装的**损失评估**应与技术根因分开陈述，避免把未验证的因果写进结论；
4. 更早版本的写入签名（保护态 DACL + `Delete` 拒绝 + Medium 标签）与 0.2.2 的签名（`FILE_DELETE_CHILD` 拒绝 + Low 标签）之间的版本边界未逐版确认。

---

## 11. 附录：检测工具

同仓库发布的 `dsh-workspace-acl-guard` 提供只读检测：

- 读取 owner、DACL、SACL 标签、保护态、有效 `WRITE_DAC/WRITE_OWNER`；
- 识别已知的两代 DSH 写入签名；
- 按目录角色（系统文件夹 / 应用目录 / 代码仓 / 普通目录）给出风险等级；
- 记录基线，后续可对比出“哪一刻、哪条 ACE 变了”；
- **不写任何 ACL**。

用法见仓库 README。
